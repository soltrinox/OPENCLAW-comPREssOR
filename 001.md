# OpenClaw compressor: purpose, reasoning, formalization, and how to judge utility

This document is a long-form companion to `SPECS.md`. It is written in paragraph form so public README copy, ClawHub listing text, developer onboarding, and research notes can be drawn from a single narrative. It does not replace the module map or task DAG. It explains why the plugin exists, how the packer is formalized, which metrics a developer should compute, what results are reasonable to expect before those metrics exist, and how to decide whether the plugin is useful on a given Gateway. Measurement of billed cost, recall, and compact-call elimination is left to implementers; methods belong in `docs/RESEARCH.md`. Cursor inject-path cards from the comPREssOR IDE extension are a related prior on a different host and must not be copied into OpenClaw marketing as this plugin’s results.

## Purpose

The purpose of the OpenClaw compressor plugin is to change what the model sees on each run of a long-lived Gateway session. OpenClaw already persists transcripts, injects workspace files, lists tools and skills, and, when the window fills, summarizes older turns with another model call. That last step is compaction. It is a reasonable default for a product that must keep chatting after the context window is full. It is also a blunt instrument. A prose digest can drop a file path, an open item, a UUID, or a Cloud Run URL. OpenClaw’s own `identifierPolicy: "strict"` exists because summarizers lose opaque identifiers. A twenty-thousand-token recent tail exists because operators do not trust the digest alone. The compressor’s purpose is to substitute that pair—growing transcript plus LLM digest plus oversized tail—with a local dual-state store and a budgeted text pack that the context engine returns from `assemble()`, plus a typed checkpoint from `compact()` that does not call the conversation model.

The plugin is not a new language model. It is not codebase retrieval. It is not a replacement for `MEMORY.md`, dreaming, or `memory_search`. It is a context-assembly mechanism. The operator installs it as a ClawHub package, sets `plugins.slots.contextEngine` to `compressor`, and restarts the Gateway. If the engine throws, OpenClaw quarantines it and continues on `legacy`. If the operator uninstalls the plugin, the slot returns to `legacy`. The purpose is therefore scoped: opt-in assembly policy, reversible, fail-open, text-only at the model boundary.

A second purpose is continuity across channels without replaying every tool dump. OpenClaw sessions live on Telegram, Discord, WebChat, iMessage, and CLI. They accumulate exec output, browser snapshots, and retries. Continuity that matters is usually small: which file is in scope, which decision was accepted, which test is failing, which identifier must not be paraphrased. The compressor extracts those into a graph, keeps a bounded numeric digest of recent chunks, and packs HOT_SET, typed lines, ranked spans, and matrix-backed sidecars under a budget. The model receives ordinary text. Local SQLite, safetensors, and span files stay on disk.

A third purpose is to give developers a host where the packer can actually replace messages. In Cursor, comPREssOR injects `additional_context` and cannot strip native Agent Chat history. In OpenClaw, a context engine’s `assemble()` return value is the conversation the embedded runner sends. That is a stronger substitution point. The plugin exists to use that slot, not to fight OpenClaw core with a megapr that rewrites `legacy` for every user.

## Reasoning: why this problem is structural

Context windows are finite. Session transcripts are not. If $H_t$ is the accumulated history through turn $t$, then $|H_t|$ is nondecreasing as turns add user text, assistant text, and tool results. Sending $H_t$ on every run makes prompt cost track session length rather than the new request. Short chats tolerate that. Multi-hour Gateway agents, group channels, and subagent trees often cannot.

OpenClaw’s default response is to keep $H_t$ until a threshold, then replace a prefix with a summary $S$ while keeping a recent tail $T$. The next prompt is roughly system prompt plus $S$ plus $T$ plus tools. Two failure modes follow. First, $S$ is generated by a model and is not guaranteed to retain the entities the next turn needs. Second, $T$ is large by default, so the “compacted” prompt is still last-N at twenty thousand tokens plus a digest. Compaction also spends a model call. That call has latency and tokens of its own. Memory flush tries to save notes to disk before the digest, which is a third model-adjacent turn and still depends on the agent writing the right Markdown.

The compressor’s reasoning is that extraction plus budgeted projection can retain typed entities more reliably than a one-shot digest, and that a small raw tail plus a pack can be a better prompt than a large raw tail plus a digest. The reasoning is not that smaller is always better. A vocabulary bag can be tiny and empty of the terms the task needs. The Python engine already treats fixture `entity_recall` as a term-hit proxy for that failure. The `recall-0.5` profile exists to admit more of each turn into the matrix and to read spans back into the pack, so retention can rise without returning to full replay. Whether 0.5 is hit on a given corpus is a research result, not a slogan.

The reasoning for shipping as a plugin rather than a core pull request is ownership. OpenClaw already defined `registerContextEngine` and an exclusive slot. lossless-claw already occupies that pattern. A core PR that replaces `legacy` would change every Gateway, couple the packer’s release to OpenClaw betas, and turn a packer bug into a platform incident. A plugin keeps quarantine, uninstall, and versioned `pluginApi`. Small host-contract PRs remain valid if `assemble()` cannot drop messages, if limits lack a token budget, or if `commitTurn` cannot round-trip. Those are seams. They are not the packer.

The reasoning for dual state rather than graph-only or matrix-only is complementary failure modes. A graph without ranking under-selects verbatim spans. A matrix without labels cannot say OpenItem versus abandoned log line. The packer uses both: HOT_SET and typed lines from $G_t$, cosine rank over candidates, and span expansion from sidecars associated with $C_t$ rows. Pattern-1 vocabulary decode is not the default forward channel because a bag of words can win size and lose every fixture term.

The reasoning for `ownsCompaction: true` is that leaving LLM summarization in place would keep the sloppy path. A no-op `compact()` on a non-owning engine is unsafe because it disables `/compact` and overflow recovery. The plugin must implement compact as a typed checkpoint: flush the graph, freeze a snapshot, write HOT_SET and identifier lines, keep session identity when possible.

The reasoning for not owning the memory slot is that OpenClaw memory is a different product: Markdown files, embeddings, dreaming, `memory_search`. The engine should prepend host-prepared memory via `buildMemorySystemPromptAddition`. Optional append of compact notes to `memory/YYYY-MM-DD.md` is a writer, not a takeover.

## What the operator should believe before installing

The operator should believe three things, and only three, before they have their own probe. First, the plugin will try to return a shorter conversation view than the full transcript, plus a labeled pack, and will try not to call a model to compact. Second, if it fails, chat continues on `legacy`. Third, local state will appear under `~/.openclaw/context-graphs/` unless they change `stateDir`. They should not believe a dollar amount, a universal quality lift, or that Cursor’s inject-path arithmetic applies to their Telegram bot. Those require a Gateway probe on their models and their traffic.

## Narrative of a turn

A message arrives on a channel. The Gateway routes it to a session. The compressor engine’s `ingest` receives the user text unless the event is a heartbeat. Heartbeats are skipped so scheduled pings do not fill $C_t$. The handle calls `step` with role user. The producer chunks the text, hashes n-grams into rows, and `append_then_pool` merges until at most $K_{\max}$ live rows remain, except protected path, decision, and identifier rows which do not EMA-merge. The graph extracts topics, facts, open items, events, paths, and identifiers. Working `graph.json` is written so a restart can bootstrap.

When the agent run starts, `assemble` loads $S_t=(G_t,C_t)$. It takes the host message list and cuts a recent tail under `keepRecentTokens`, never splitting a tool call from its result. It samples a pack: HOT_SET, typed projection, ranked chunks, matrix span readout, under $B_t$. It prepends OpenClaw memory addition. It returns tail plus `systemPromptAddition`. The model sees that, not the full SQLite transcript.

After the run, assistant text and tool gists ingest. `commitTurn` records `advancementKey` so retries do not double-write. If the window overflows or the user runs `/compact`, `compact` writes a typed checkpoint without an LLM. Subagent spawn copies parent HOT_SET and identifiers, not twenty thousand tokens. On engine error, OpenClaw quarantines and uses `legacy` for the process.

That story is the product. Everything else is knobs, packaging, and measurement.

## Formalization

Let $t$ be the turn index as persisted by the handle. Let $q_t$ be the current user prompt, or the last user turn if assemble has no fresh prompt. Let $H_t$ be the full session history the host could send. Let $G_t$ be the symbolic graph. Let $C_t\in\mathbb{R}^{k\times d}$ be the live gist matrix with $k\le K_{\max}$ and default $d=256$. Dual state is $S_t=(G_t,C_t)$. The packer $\Pi$ emits text $P_t=\Pi(S_t,q_t;B_t)$. The assembled prompt the embedded runner sends is not $H_t$. It is a recent tail $T_t$ plus $P_t$ plus host system prompt, tools, and memory sections. Write $A_t=T_t\oplus P_t$ for the engine-controlled portion.

The internal token estimator used for packing is character-based. For nonempty text $x$,

$$
\tau(x)=\max\left(1,\ \left\lfloor\frac{|x|+3}{4}\right\rfloor\right),\qquad \tau(\varepsilon)=0.
$$

This is `estimate_tokens` in the Python engine. It is not tiktoken and not a vendor invoice. Developers who compare arms must either use $\tau$ on both arms or use the host tokenizer on both arms. Mixing units is not a result.

The packing constraint is

$$
\tau(P_t)\le B_t\le B_{\max}.
$$

Cursor defaults used $B_{\max}=1024$. The OpenClaw `recall-0.5` profile uses a larger cap (2048 in `SPECS.md`) so ranked chunks and span readout have room. Novelty scaling in the Cursor packer is

$$
B_t=B_{\max}\quad(t\le T_w),\qquad
B_t=\max\big(T_{\mathrm{floor}},\ \min(B_{\max},\ \lfloor B_{\max}\cdot\max(\rho_{\min},r_t)\rfloor)\big)\quad(t>T_w),
$$

with warmup $T_w=3$, floor tokens $T_{\mathrm{floor}}=64$, and novelty floor $\rho_{\min}=0.5$. For OpenClaw long sessions, `SPECS.md` sets `noveltyBudgetFloor` to 1.0 so $B_t$ does not shrink when the session is long but still changing in ways novelty may miss. Developers should treat that as a profile choice and measure whether a high floor wastes budget on repetition.

Hashed n-gram embedding maps text to a unit vector in $\mathbb{R}^d$ by accumulating signed hashed 1–3 grams, then L2-normalizing. Ranking score is cosine:

$$
\mathrm{score}(q,c)=\cos\big(\hat v(q),\hat v(c)\big).
$$

The engine keeps chunks with score at least $\theta=0.03$, else the top $k_{\mathrm{fb}}$ chunks. Cursor used $k_{\mathrm{fb}}=3$. The OpenClaw profile uses 8. Raising $\theta$ toward 0.5 would filter more chunks out; 0.3 to 0.5 in this project is a retention target for fixture term-hit rate, not a cosine floor.

Append-then-pool stacks new rows under $C_{t-1}$ and, while $k>K_{\max}$, replaces the adjacent pair of highest cosine with an EMA blend $c'=\alpha c_i+(1-\alpha)c_{i+1}$. Cursor used $\alpha=0.7$, $K_{\max}=32$, and at most eight chunks per turn. The OpenClaw profile uses $\alpha=0.5$, $K_{\max}=64$, sixteen chunks per turn, and never-merge rows for path, decision, and identifier tags. The matrix still does not ship as floats. Span sidecars hold wording. Readout selects sidecar text for rows similar to $q_t$.

Pack assembly concatenates ordered families while the prefix stays under $B_t$: HOT_SET, then typed lines, then graph-ranked chunks, then matrix spans. Marginal Jaccard skip is $J(A,B)=|A\cap B|/|A\cup B|$ with threshold $\mu$. Cursor used $0.8$; the profile uses $0.92$ so near-duplicate lines that still carry a term are less often dropped. HOT_SET shares remain $s_{\mathrm{open}}=0.40$, $s_{\mathrm{decision}}=0.40$, $s_{\mathrm{path}}=0.20$. Node rank inside a bucket is $\mathrm{salience}(n)+0.5\,J(\mathrm{keywords}(n),\mathrm{keywords}(q))$. Slot count is about $\max(5,\lfloor M/64\rfloor)$ for HOT_SET character budget $M$, with $M=800$ under the OpenClaw profile versus 400 in Cursor.

If a developer defines a replay arm $R_t$ as the text that would have been forwarded without packing (full ingest, or full assemble messages), then volume identities

$$
\Delta=\sum_t\tau(R_t)-\sum_t\tau(P_t),\qquad
\eta=1-\frac{\sum_t\tau(P_t)}{\sum_t\tau(R_t)}
$$

are well-defined under $\tau$. They are not billed savings. On OpenClaw, a more relevant pair is $\Delta_A$ and $\eta_A$ using assembled engine-controlled text $A_t$ versus legacy assembled text $L_t$, preferably with the host tokenizer. Compact-call count $N_{\mathrm{llm}}$ on the compressor arm should be zero while the engine is healthy. Fixture term-hit

$$
\mathrm{entity\_recall}(\mathcal{R},P)=\frac{|\{r\in\mathcal{R}: r\text{ occurs in }P\}|}{|\mathcal{R}|}
$$

is a proxy over a reference set $\mathcal{R}$ of paths, quoted items, and headings. The Python tests currently gate at 0.3. The profile name `recall-0.5` means implementers should try to lift that proxy on a comparable fixture by admission and readout, and should also track pollution so tool dumps do not evict OpenItems.

Informal utility per token, as used in comPREssOR theory docs, is the sketch $\max_{P:\tau(P)\le B} U(P;q)/\tau(P)$ subject to retaining active entities. Ship code does not optimize $U$. It runs a fixed policy $\Pi$. Developers who want $U$ must define a task score (pass/fail of a scripted agent job) and divide by host tokens. That experiment is research.

## Expected results (qualitative, before a probe)

Before any number is published, the expected behavioral results are as follows. On a healthy install, `openclaw doctor` shows slot `compressor`. Assemble returns fewer messages than the raw transcript on a long fixture, with tool pairs intact in the tail. The system prompt addition contains labeled lines such as OpenItem, Fact, Path, Event, and a STATE line. Compact does not invoke the conversation model in unit tests that stub the host. Heartbeats do not create new matrix rows. Engine crash does not block chat. Uninstall restores `legacy`. State files appear under the configured root. Sidecar health fails closed to doctor if Python is missing on the 0.1.0 path.

Expected retention behavior, if extractors see explicit paths and open items, is that HOT_SET still contains those lines after many tool-heavy turns, more often than a generic LLM summary would. Expected failure, if the user never writes durable facts and tools emit huge logs, is a pack that is cheap and thin. Expected failure if `keepRecentTokens` is raised back to twenty thousand is that the plugin becomes last-N with extra labels and little volume win. Expected difference versus Cursor is that billed input can move if assemble actually drops history; Cursor inject could not prove that.

Expected operational results: sidecar latency is a new cost; v1.1 TypeScript engine should remove Python from the critical path. Subagent children should start from HOT_SET rather than a copied transcript. Group chats should not ingest every bystander’s message into $C_t$ if mention rules are wired.

None of these expected results is a published $\eta$. After `scripts/probe-openclaw.sh` exists, expected research outputs are two-arm logs: compact count, overflow retries, assembled token estimates, pack $\tau$, identifier presence checks the implementer defines, and optional provider usage. Whether $\eta_A$ is large depends on how fat the legacy tail was and whether Codex still sends native history.

## Metrics a developer should use

Use a small closed set and name the unit every time.

Volume: $\tau(P_t)$, $\tau(T_t)$, $\tau(A_t)$, host `estimatedTokens` from assemble, and provider billed input if the Gateway exposes it. Report them separately. Do not add them into one “tokens saved” headline until you know they are the same unit.

Reduction: $\eta$ under $\tau$ for pack versus a declared replay definition; $\eta_A$ under host tokens for compressor assemble versus legacy assemble. State the replay definition in the log header.

Retention: `entity_recall` on a frozen reference set; identifier hit rate; open-item hit rate; path hit rate. Pollution: fraction of HOT_SET lines that are tool-log fragments or preamble (“let me”, “running”). Graph caps: active node counts versus MAX_ACTIVE_*. Matrix: $k/K_{\max}$, count of protected rows, merge count per turn.

Lifecycle: compact LLM calls (should be zero), overflow retries, assemble latency, sidecar RPC latency, quarantine events, heartbeat skip count, commitTurn duplicate versus committed.

Task: a scripted job that requires a path and a decision from turn 1 at turn 20. Pass/fail is stronger than term-hit. Run both engines.

Cost: if you must talk money, convert provider billed tokens with the operator’s price sheet on that day, and label it as such. Do not convert $\tau$ to dollars.

Dashboard telemetry, if built as in the dashboard plan, should chart $\tau(P_t)$ versus a replay estimate, $k/K_{\max}$, pack composition (HOT_SET vs typed vs ranked vs spans), and sidecar latency. It should not invent USD. It should not render raw vectors.

## How a developer determines usefulness

Usefulness is not a single scalar. A developer should ask four questions on their traffic.

Does the next turn still see the active file, the open item, and the identifier without the full transcript? If yes, the pack is doing continuity work. If no, either extraction missed (write facts more explicitly, or improve extractors) or budget/tail policy starved the pack (raise `forwardBudget` or inspect pollution).

Does assembled host-token volume fall relative to `legacy` on the same model without a rise in overflow retries or task failures? If volume falls and tasks still pass, the plugin is useful as a context budget control. If volume falls and tasks fail, it is a harmful compressor. If volume does not fall, assemble may not be replacing messages (Codex native history, or `keepRecentTokens` too large).

Does compact stop calling a model, and does the typed checkpoint still contain identifiers? If yes, you removed a class of cost and a class of drift. If compact still fails and quarantines to legacy, the plugin is not owning compaction in production.

Is operational cost acceptable? Sidecar timeouts, Python provisioning, and disk growth under `context-graphs/` are real. If the Gateway is a small VPS without Python, wait for `engineImpl=ts` or provision a venv. If disk grows without bound, add purge and graph caps. Usefulness includes operability.

A practical protocol: install `-l`, set the slot, run `openclaw doctor`, run a ten-turn fixture with one large tool result and one UUID, dump `/context json` and stage logs, compare to `legacy` on a second agent, and write the numbers in `docs/RESEARCH.md`. If identifier and path survive and assembled size is lower, keep the plugin. If not, do not publish ClawHub copy that implies they do.

## Suggested public-facing materials

ClawHub listing and README should follow mechanism, outcome, scope. Mechanism: local graph and bounded matrix; `assemble` returns a small tail plus a pack ordered HOT_SET, typed facts, ranked spans; `compact` writes a typed checkpoint without an LLM. Outcome: the operator can keep a long Gateway session inside a budget with labeled continuity for paths, open items, and identifiers, and can uninstall to `legacy`. Scope: opt-in context engine; not memory-core; not RAG; not a quality guarantee; native plugin trust (in-process); Python required on 0.1.0; measurement is the operator’s probe.

Do not put Cursor PERFORMANCE cards in the listing. Do not say unbreakable memory. Do not say it replaces OpenClaw memory files. Do say exclusive slot, doctor, fail-open, state directory, and how to revert.

Install snippet should be the three lines: install ClawHub spec, set `plugins.slots.contextEngine` to `compressor`, restart, `openclaw doctor`. Config snippet should show `profile: "recall-0.5"` and point to `SPECS.md` for knobs. A short “what the model sees” example of a HOT_SET block helps more than a metaphor.

A comparison paragraph should name lossless-claw as another context engine (DAG plus originals) and this plugin as query-conditioned typed packing under a budget. Users pick one slot. Do not claim uniqueness of “using a graph.”

Security paragraph: in-process plugin equals Gateway trust; no assemble-time network; no API keys in plugin config; state is local; uninstall does not delete graphs unless purge.

A “when not to use” paragraph: short sessions where the transcript is already smaller than the pack budget; tasks that need exact full-source quotation (attach the file); hosts that cannot run Python until 0.2.0; operators who will not inspect `/context` when something is forgotten.

Developer-facing docs should split. `SPECS.md` remains the contract: modules, DAG, constitution. CHANGELOG is semver: sidecar, TS engine, middleware.

For API docs, document `claw_cli` JSONL commands: step, sample, flush, expand_spans, health. Document that Cursor `hook_cli` additional_context JSON is not this protocol. Document `commitTurn` statuses. Document hostRequirements. Document that Codex may still own native history.

## Suggested details that augment SPECS for implementers

Name the replay definition in every script: “full host messages before engine” versus “user-visible transcript” versus “chars of ingested tool results.” They differ.

Prefer host tokenizer for assemble comparisons when `runtimeSettings.limits` exists; keep $\tau$ for packer internals and for golden tests against Python.

Log pack method (`hot_set`, `query-pack`, `extractive+hot`, `skip`) because skip on unchanged open items can look like a bug.

Preserve tool-call/result pairing in the tail even if it blows a little past `keepRecentTokens`; a split pair is worse than a slightly large tail.

Treat identifiers as first-class facts with `kind_hint=identifier` and protected matrix rows. Compact entries must copy them verbatim. This is the substitute for `identifierPolicy` when you own compaction.

Skip `isHeartbeat`. Ingest tool results as gists, not as full dumps in the tail, while storing capped spans for readout.

Do not enable Pattern-1 to chase entity_recall. If readout and HOT_SET cannot hit the research target, change extractors, budget, or protected rows, not vocab decode.

For `commitTurn`, store the inclusive message range keyed by `advancementKey` next to `meta.sqlite`. Duplicate must be a no-op. Without the fence, OpenClaw ignores the engine for the logical turn.

For bootstrap, ingest visible transcript through the cursor API rather than assuming graph.json survived. Empty graph plus nonempty transcript is a recovery path, not an error.

For subagents, copy HOT_SET and identifier vault only. Merge child OpenItems on end with `derived_from`. Do not duplicate parent $C_t$ unless research shows it helps.

For ClawHub, point `runtimeExtensions` at `dist/index.js`. Include the wheel and skill in `npm pack`. Pin `pluginApi`. Test betas. Dry-run publish.

For doctor, fail if the slot says compressor but the plugin is disabled, if stateDir is not writable, if sidecar Python is missing on sidecar profile, if `keepRecentTokens` is so large that the operator is back to last-N. The last check is a warning, not a hard error, because some operators will want a fat tail on purpose.

## Reasoning about the 0.3 to 0.5 profile

The number 0.3 in the Python tests is a fixture gate on `entity_recall`, not a matrix fill fraction. The SDK-style probe on the IDE engine reported a higher but still partial term-hit rate on a different corpus. Naming an OpenClaw profile `recall-0.5` means: admit more chunks into $C_t$, blend new rows more strongly (lower EMA), protect entity rows from merge, enlarge HOT_SET and $B_{\max}$, loosen Jaccard skip, disable novelty shrink, and read spans back into $P_t$, then measure whether the same class of fixture retains more reference terms without drowning HOT_SET in tool logs. It does not mean set cosine $\theta$ to 0.5. It does not mean half the transcript. It does not mean half of task quality.

If research shows 0.5 term-hit only when the tail is grown to twenty thousand tokens, the profile has failed and last-N is doing the work. If term-hit rises and pollution stays bounded and assemble volume falls, the profile is doing the intended job. Publish the method, not a borrowed percentage from another product.

## Formal objects and code map (for docs footnotes)

$\tau$ is `metrics.estimate_tokens`. $\Pi$ is `pack.pack_forward`. Dual state is `handle.PersistentAgentHandle` plus `graph.CtxGraph` plus `store.StateStore`. Embed is `producer.hashed_ngram_embed`. Rank is `rank.rank_chunks` / `rank_relevant_chunks`. Pool is `compress.append_then_pool`. HOT_SET is `graph.hot_set`. OpenClaw mapping is `assemble`, `ingest`, `compact`, `commitTurn` in the plugin TypeScript host. Sidecar protocol is `claw_cli.py`, not `hook_cli.py`. State schema remains `ctx-graph/v1` and `state-node.v1`. These names should appear in developer docs so a reader can grep the engine without re-deriving constants from prose.

Constants that public docs may list as profile defaults, not as proven optima: $K_{\max}=64$, chunks per turn 16, $\alpha=0.5$, $B_{\max}=2048$, HOT_SET 800 characters, `keepRecentTokens=4000`, $\theta=0.03$, $k_{\mathrm{fb}}=8$, $\mu=0.92$, novelty floor 1.0, graph caps 48/48/64, protectKinds path/decision/identifier. Cursor-parity profile restores the IDE defaults for A/B.

## Worked examples for $\tau$, packing, and recall

A developer who has never opened `metrics.py` still needs to trust the packing unit. Take the four-character string `abcd`. Its length is 4, so $\tau=(4+3)//4=1$. Take `abcde` with length 5: $\tau=2$. The empty string is the only input that returns 0, which matters when a skip path emits no pack: that turn must not be treated as having spent one estimated token in a fill-rate that divides by $\tau(P)$. Whitespace-only strings are nonempty under Python `len`, so they receive at least one estimated token if packed. Truncation that targets roughly $B\times 4$ characters is the inverse sketch of $\tau$. If a packer log says packed_tokens=800 under $\tau$, a host tokenizer may report a different integer. Both can be true. The README should say “estimated tokens (chars/4)” wherever $\tau$ is shown, and “provider usage” wherever a Gateway export is shown.

Consider a toy session in which the user writes: create todo “buy groceries” and add path `docs/README.md`. The graph should emit an OpenItem and a path fact. The assistant later marks milk done. HOT_SET should still mention groceries or bread if those remain open, and should not spend its entire budget on a subsequent npm install log. A fixture `entity_recall` over the set {groceries, README.md} is then 0, 0.5, or 1 depending on whether those strings appear in $P_t$. That is the entire meaning of the 0.3 gate in the Python tests: on a small labeled set, at least some terms survive. Lifting the research target to 0.5 on a similar set means one more term on a two-term set, or three of six on a six-term set. It is easy to game by stuffing the tail. The pollution metric exists so that game is visible.

A second toy is an opaque identifier. Suppose a Cloud Run URL appears once in a tool result. LLM compaction may paraphrase it. The compressor should store a Fact with kind_hint identifier, protect the row from EMA merge, and copy the URL into the compact entry and into HOT_SET or typed lines. A useful probe is binary: after compact, does the next assemble still contain the exact URL. That probe is more honest than a blended $\eta$.

A third toy is overflow. Legacy compact plus retry costs a summarizer call. The compressor compact should cost a graph flush and a string write. A probe that counts `N_{\mathrm{llm}}$ on each arm tells you whether ownsCompaction is real in production, independent of whether billed input moved.

## What the model sees, in words a README can reuse

The model never sees a matrix. It never sees SQLite. It sees a short recent conversation, possibly including the last tool pairs, and a block of additional system text that looks like a labeled briefing: open items first, then decisions and paths, then a few verbatim spans that ranked like the current question, then a STATE line with session and turn ids. If the briefing lacks the file you care about, the plugin did not supply it. Attach the file or say the path again. That paragraph is the correct user-facing explanation of dual state.

A longer listing paragraph can add: install from ClawHub, set the slot to compressor, restart, run doctor. Default profile recall-0.5 enlarges matrix admission and pack budget relative to the Cursor IDE defaults; cursor-parity restores those defaults for comparison. ## Developer determination procedure, expanded

Afternoon protocol, written so a CONTRIBUTING doc can paste it. First, link-install the package and enable the plugin without setting the slot. Confirm doctor lists compressor as installed and not selected. Second, set the slot and restart. Confirm doctor shows contextEngine compressor. Third, send a single message in WebChat. Confirm a session directory appears with graph.json. Fourth, send a message that includes a path and a quoted open item. Confirm HOT_SET in the stage log or in `/context` if you surface the addition. Fifth, run a command that produces a large tool result. Confirm the tail still pairs tool call and result, and that the pack is not only the log. Sixth, run `/compact` if the session is large enough, or force compact in a test. Confirm no second model is required in the unit host and that identifiers remain. Seventh, kill the sidecar or point pythonPath at a missing binary. Confirm the next user message still gets a reply via legacy quarantine. Eighth, switch the slot back to legacy. Confirm behavior returns. Ninth, only if you care about volume, run two agents on the same fixture and write both `/context` sizes and any usage footer into RESEARCH.md with the date, model id, and plugin version.

If step four fails, usefulness is not yet there: extraction or assemble is not projecting. If step five fails by stuffing the log, usefulness is negative: you paid packer complexity to forward noise. If step seven fails by hanging the Gateway, do not ship. If step nine shows no volume change on the embedded runner, assemble may still be passing most messages through; inspect keepRecentTokens and whether messages in the assemble result were actually truncated.

A developer integrating in a company Gateway should add a tenth step: run the fixture on the models they actually pay for, because compact-call elimination is model-priced and assemble volume is model-priced. A local Ollama compact model versus Claude compact is a different $\Delta$ even if $\tau(P_t)$ is identical.

## Relation to memory, pruning, and lossless-claw

OpenClaw pruning trims old tool results in memory for a request and does not rewrite the transcript. The compressor may still see those tools at ingest if they were persisted. Middleware that shrinks tool results before they re-enter the model is the durable complement. Public docs should not say the plugin replaces pruning. They should say pruning still runs, and the plugin additionally gists tools into the graph.

OpenClaw memory files are the long-term store. The pack is the per-run briefing. A fact only in MEMORY.md and truncated by bootstrap limits may still be missing from the model. A fact only in the pack and never written to MEMORY.md may vanish after purge. Developers should treat promoteMemoryNotes as an explicit bridge, default off, so dreaming and search are not surprised by silent writes.

lossless-claw, as described in OpenClaw’s context-engine docs, stores originals and summarizes into a DAG. This plugin stores extracts and a digest and packs under a query. Both are valid engines; only one slot is active. A comparison sentence for docs: lossless-claw optimizes for not losing original messages; compressor optimizes for a bounded labeled view of what is active now. Users who need verbatim week-old tool output may prefer originals in a database. Users who need the current open item and the URL to survive a compact without another model call may prefer this packer. Neither sentence should declare a winner on $\eta$.

## Failure modes to document honestly without a scoreboard

Extraction miss: the user implied a decision in vague prose. The graph has no Fact. The pack cannot invent it. Mitigation: write “Decision: …” once. Docs should teach this; it is the same lesson as the Cursor extension.

Rank miss: the term is in a span sidecar but cosine is low and fallback k is exhausted. Mitigation: raise rankFallbackTopK, raise budget, or put the term in an OpenItem.

Merge smear: unprotected rows blend until no row is close to the query. Mitigation: protectKinds and lower EMA.

Budget starve: HOT_SET fills $B_t$ and ranked spans never enter. Mitigation: raise forwardBudget or shrink HOT_SET max_chars if HOT_SET is noisy.

Tail swallow: keepRecentTokens is so large that pack savings cannot appear in billed input. Mitigation: lower the tail and re-probe.

Host leftover: Codex native history still contains the transcript. Mitigation: scope claims to the embedded runner until a Codex-specific probe exists.

Quarantine: a thrown assemble disables the engine for the process. Mitigation: fail only on hard errors, not on empty packs; log the throw.

Sidecar hang: JSONL deadlock. Mitigation: timeouts and always-exit-0 with ok:false.

State mix: operator points stateDir at Cursor’s context-graphs. Mitigation: default to `~/.openclaw/context-graphs/` and document the overlap.

Skill confusion: users install only SKILL.md and expect compression. Mitigation: listing must say the skill does not assemble; the engine slot does.

## Formalization notes for a math appendix in public docs

Public math should be short. Dual state $S_t=(G_t,C_t)$, pack $P_t=\Pi(S_t,q_t;B_t)$, constraint $\tau(P_t)\le B_t$. Ordered families $u_1\prec u_2\prec u_3\prec u_4$. Cosine rank with floor $\theta$. Pool EMA with optional protected set $\mathcal{P}$ of rows that skip merge. Volume $\eta$ only with a defined replay arm and a defined unit. Do not display the Cursor corpus sums 862201 and 139465 as OpenClaw results. If you mention them at all, say they are IDE inject-path measurements on another host. The safer choice is not to mention them in the plugin README.

Adaptive budget equations can live in an appendix for developers who will implement `pack.py` parity in TypeScript. Operators do not need $T_w$ on the ClawHub page.

HOT_SET shares 0.40/0.40/0.20 are engineering quotas, not information-theoretic allocations. Docs can say “about two-fifths open work, two-fifths decisions, one-fifth paths” if they also say the remainder of the pack is ranked spans under the leftover budget.

The informal program $\max U/\tau$ should be labeled informal. Implementers who run task pass/fail divided by host tokens are approximating $U/\tau$. That is a research metric, not a dashboard KPI, until the task set is frozen and repeated.

## Extended purpose: what success looks like for the project, not for a single metric

Project success at 0.1.0 is a ClawHub-installable engine that an operator can select, that assembles a tail and a pack, that compacts without an LLM in tests, that fails open, and that has a probe script someone can run. Project success at 0.2.0 is the same without Python. Project success at 0.3.0 is tool middleware and a Control UI that shows pack composition and sidecar health. Project success is not a particular $\eta$. If a probe later shows a large $\eta_A$ on embedded OpenClaw with stable tasks, that is a research success to document. If it shows little $\eta_A$ but zero compact LLM calls and better identifier survival, that is also a success of a different kind: quality of compact, not volume of assemble. Public docs should allow both stories instead of forcing a single percentage.

## Extended reasoning: attention, not only tokens

Even when billed input does not move, a typed pack can change what the model attends to. A twenty-thousand-token tail buries a one-line decision. HOT_SET puts that line first. Usefulness can therefore appear as fewer “what file were we editing” turns rather than as a smaller invoice. Task-level metrics catch that. Volume metrics alone do not. Developer materials should recommend at least one task metric in every probe that claims usefulness, even if the task is as small as “after twenty turns, edit the same path named in turn one.”

## Extended reasoning: fail-open as a product feature

Operators will not adopt a plugin that can silence Telegram. Quarantine to legacy is not a shame condition; it is the contract. Docs should tell operators to look at stage logs when packs disappear, not to assume the plugin is working because chat still works. That distinction is the same as the Cursor hook fail-open lesson and should be restated for OpenClaw.

## Closing


OpenClaw already solved “keep chatting when the window is full” with summarization and a fat tail. This plugin proposes a different policy: extract typed state continuously, bound the numeric digest, pack under $\tau(P_t)\le B_t$, replace assemble messages, and compact without an LLM. The purpose is continuity per token with fail-open install. The reasoning is structural growth of $H_t$, known digest drift, and a host slot that can actually drop history. The formalization is dual state, hashed cosine rank, EMA pool with protected rows, ordered packer, and volume identities under a named estimator. The metrics are volume, reduction, retention, pollution, lifecycle, task pass/fail, and optional billed tokens, never mixed silently. The expected result before research is behavioral: bounded assemble, typed compact, quarantine, revert. The expected result after research is whatever the probe says, written by the people who ran it. Public materials should repeat mechanism, outcome, and scope until that is the only story the listing tells.

A developer who has read this file and SPECS.md has enough to implement Package 0 without inventing a product claim. They know that utility is continuity of paths, open items, and identifiers per forwarded token, judged with a named unit and a task, not with a single inherited percentage.
